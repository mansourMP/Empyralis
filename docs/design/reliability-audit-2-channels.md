## Architecture split (fact, not opinion)

Two structurally different implementations exist under the umbrella "channels":

1. **Gateway-resident personal channels** — Telegram-personal, WhatsApp-personal, Signal, iMessage, WeChat. Code lives in `empyralis-gateway/src/channels/` + `empyralis-gateway/src/bridges/`, runs on the user's paired Agent Computer, reports state up to the server via a publisher/registry.
2. **Server-resident business/bot channels** — Telegram-bot (hosted), Discord-bot, Slack, Email. Code lives entirely in `server_modules/*.py`, runs in the cloud control-plane process, no Agent Computer involved.

Within (1) there's a further split: Telegram/WhatsApp are **socket-based** (GramJS MTProto / Baileys WebSocket) with a shared exponential-backoff reconnect policy. Signal/iMessage/WeChat are **poll-based**, riding a shared `LocalBridgePersonalChannelRuntime` that polls a third-party bridge process's HTTP surface every ~5s and has **no reconnect/backoff concept at all** (`reconnectAttempts` is hardcoded to `0`).

## Notes per channel

### Telegram — personal
Documented, previously-real, now-fixed production bugs, all with in-code comments:
- **GramJS logger crash**: internal `_log` object missing methods (`canSend`/`warn`/etc.) crashed the update loop; root-caused to `npm install` (not `npm ci`) letting Agent Computer boxes resolve mismatched GramJS 2.x builds — `telegram/runtime.ts:349-440`, specific version-mismatch evidence at `:376-382`. Fixed via `ensureGramLoggerShape()`/`createGramLoggerShim()` (`:411-440`).
- **Family-group misaddressing**: Telegram's own `mentioned` bit fires on any reply to a message the peer (the human owner, for a full-account session) sent — replies to the owner in a group were misread as bot-directed. Fixed via `hasExplicitTelegramMention()` — `runtime.ts:499-525,630-648`.
- **Broadcast-channel public leak**: a channel post @-mentioning an unrelated username matching the account's own username triggered a live reply posted publicly into the broadcast channel. Fixed via `isBroadcastTelegramChat()` — `runtime.ts:592-608`.
- **Self-chat echo loop**: own sent replies into self-chat re-enter as inbound events. Guarded by `isOwnSelfChatEcho` + a breaker capped at 6 turns/60s (`SELF_CHAT_BREAKER_MAX_TURNS`/`_WINDOW_MS`) — `runtime.ts:482-496,1650-1674`.
- **Cross-chat message-id collision**: a flat `Set` of sent-ids collided across chats (Telegram ids are per-chat, not global), falsely resolving `is_reply_to_sage=true` in an unrelated group. Fixed with a per-chat `Map` — `runtime.ts:766-782`.
- **Typing-indicator hang**: TTL reduced from 5 min to 90s (`TELEGRAM_INBOUND_TYPING_MAX_TTL_MS`) — `runtime.ts:442-453`.
- Manual `handleDisconnect` does a full state wipe, explicitly to prevent "a bad first attempt jam[ming] a phone number in a code_required → PHONE_CODE_INVALID → code_required retry loop with no way out short of an operator hand-editing Gateway state files" — `runtime.ts:879-886`.
- No FLOOD_WAIT/rate-limit classification anywhere; falls through to generic reconnect-with-backoff — repo-wide grep for FLOOD/rate-limit/429 in `telegram/` returned zero hits.
- Server-side catalog read treats Telegram as a **box-wide singleton session**: if the requesting agent has no session but another agent on the same box does and it's connected, that state is reflected — `connection_catalog_service.py:2120-2160`. Same box-singleton fallback exists for WhatsApp (`:2161-2176`).

### WhatsApp — personal

A process crash or disk hiccup mid write truncates the file; the very next read silently falls back to a blank identity... which looks to the owner like 'scan a new QR' even though nothing about their account actually changed" — `auth-persistence.ts:5-19`.

- Pairing-code request failures were "Previously silent — status stayed wherever it was (typically still 'connecting'), so the UI spun forever with no indication the request had actually failed" — now fixed — `runtime.ts:1516-1523`.
- Fetches the **live** WhatsApp Web client version from `web.whatsapp.com` rather than Baileys' bundled default, citing a known upstream library bug (WhiskeySockets/Baileys#2679) causing stale-version connection rejections — `runtime.ts:127-133,982-987`.

## Cross-channel infrastructure (shared machinery)

- **State keying**: `personal_channels_repository.py` keys WhatsApp/Telegram state by `(gateway_id, channel_key, agent_id)` (schema lines 51,73) — i.e. per-gateway, per-channel, per-agent. `find_agent_id_for_telegram_session` documents the current real limitation verbatim: "the Gateway runs one singleton session per process today... CURRENT (single-agent) design: return whichever agent_id most recently touched this gateway+channel... true until the Gateway itself pools multiple concurrent sessions (not built yet...)" — `personal_channels_repository.py:531-577` (comment at 538-555).
- **Two disjoint reconnect strategies** coexist under one "channels" umbrella: socket-based channels (Telegram/WhatsApp) use `foundation/reconnect-utils.ts`'s shared exponential-backoff policy (1s→30s, factor 1.8, 25% jitter, max 12 attempts); poll-based local-bridge channels (Signal/iMessage/WeChat) use no backoff at all, just a fixed ~5s poll interval with zero reconnect-attempt tracking.
- **Typing keepalive** (`foundation/typing-keepalive.ts`): generic re-fire every 3s, self-expiring at 60s via `setTimeout`. Comment documents a fixed race: a concurrent `stop()` completing while a `start()` await is in flight could otherwise arm timers after `stop()` already ran, "a permanently leaked, self-perpetuating interval" — guarded by an `if (this.stopped) return;` check (`:34-41`).
- **Inbound debounce** (`foundation/inbound-debounce.ts`): coalesces a rapid multi-message burst on one conversation into a single published `channel.inbound` event, 2000ms sliding window, keyed by `remote_jid`, media/`/command` messages bypass immediately. Comment documents a real fixed production regression: an `.unref()`'d flush timer was silently skipped by libuv at the exact quiet point after a burst, so "the message would never be published (the exact production regression this module shipped with)" — now fixed by keeping the timer ref'd (`:47-56`).
