## 1. Connection lifecycle

### Empyralis

- Connects via HTTPS POST `${apiBaseUrl}/gateway/sessions` to obtain a `ws_url`/`session_token` (`empyralis-gateway/src/cloud/ws-client.ts:207-218`), then opens a WebSocket with auth carried in the WS **subprotocol string** `empyralis.gateway.session.<sessionToken>` (`ws-client.ts:548-553`), not a header.
- `wss://` is enforced and `localhost` forbidden outside dev via `assertWebSocketUrl()` (`empyralis-gateway/src/config.ts:111-130`).
- On close: `socket.onclose` (`ws-client.ts:248-274`) stops the heartbeat loop, nulls socket state, journals `gateway.socket.closed`, and calls `handleSocketFailure(reason)` (`ws-client.ts:873-894`) which rejects in-flight `pendingResponses`, marks health state `"offline"`, and marks outbox entries for replay/uncertain.
- `socket.onerror` (`ws-client.ts:568-571`) is only wired during the initial connect handshake; there is no persistent post-connect `onerror` listener in this file.
- Reconnect/backoff exists: `ReconnectBackoff.nextDelayMs()` (`empyralis-gateway/src/cloud/reconnect.ts:27-35`) is exponential — `base = min(maxDelayMs, minDelayMs * 2^attempts)` (factor default 2, `reconnect.ts:19`), jitter `= base * 0.2 * Math.random()` (default jitterRatio 0.2, `reconnect.ts:20`), result floored at `max(250, minDelayMs)` (`reconnect.ts:34`). Defaults: `reconnectMinDelayMs=1000ms`, `reconnectMaxDelayMs=30000ms` (`empyralis-gateway/src/config.ts:145-146`).
- Driving loop `GatewayWsClient.run()` (`ws-client.ts:358-394`) is an infinite `while(true)` that reconnects on any retryable error. `classifyReconnectError()` (`reconnect.ts:38-62`) treats 401/403/token-missing/device-trust-revoked as **non-retryable** — `run()` throws and the loop exits permanently (no further reconnect attempts) on those errors.
- **The literal string "WebSocket was closed before the connection was established"** does not appear in Empyralis application code — it is the `ws` npm library's own internal error (`empyralis-gateway/node_modules/ws/lib/websocket.js:305,495`), thrown by `ws` when `.close()`/`.terminate()` is called mid-`CONNECTING`. It is not at `ws-client.ts:478` today (that line is inside `publishEvent()`'s "Gateway scope is not active" path, `ws-client.ts:472-484`).
- The related failure class **is** guarded: `openSocket()`'s 10s connect timeout (`ws-client.ts:554`) replaces `socket.onerror` with a no-op before calling `socket.close()`, with an explicit comment that closing a still-connecting socket can otherwise "throw it as an unhandled 'error' that crashes the whole gateway process on Node" (`ws-client.ts:554-563`).
- Two other comments in the file document previously-observed live crashes and their mitigations:
  - `dispatchRequestFrame()` attaches a no-op `.catch(() => {})` to avoid an unhandled-rejection crash from an orphaned rejected promise (`ws-client.ts:678-686`).
  - `dispatchRequestFrame()` re-checks socket-null state right before `.send()`, with comment: *"a close/reconnect racing in during that window nulls out this.socket. Without this, that race throws an uncaught TypeError from calling .send on null, which crashes the whole gateway process with no supervisor to bring it back (observed live: a heartbeat lost exactly this race and took the process down)"* (`ws-client.ts:700-711`).
- **No `process.on("uncaughtException", ...)` or `process.on("unhandledRejection", ...)` handler exists anywhere in production code** (`empyralis-gateway/src/index.ts`, `ws-client.ts`, or elsewhere in `src/`). The only such registrations in the repo are in test files (`empyralis-gateway/src/__tests__/heartbeat-loop.test.ts:23,71`). One comment in `empyralis-gateway/src/bridges/imsg-imessage-client.ts:189` references the concept for a different, already-mitigated child-process EPIPE case — it is not a real process-level handler.

### OpenClaw

- `src/infra/backoff.ts:17-21` — `computeBackoff(policy, attempt)`: `base = initialMs * factor^(attempt-1)`, jitter `= base * jitter * Math.random()`, result `min(maxMs, round(base+jitter))`. Same shape as Empyralis's algorithm.
- Concrete policy used for **channel transport** auto-restart: `CHANNEL_RESTART_POLICY = { initialMs: 5000, maxMs: 300000, factor: 2, jitter: 0.1 }`, capped at `MAX_RESTART_ATTEMPTS = 10` (`src/gateway/server-channels.ts:32-38`), driving per-channel restart after a channel transport dies (`server-channels.ts:719-745`); logs `"giving up after {N} restart attempts"` once exhausted (`server-channels.ts:724`) rather than retrying forever.
- `src/channels/transport/stall-watchdog.ts:20-111` — generic idle watchdog: tracks `lastActivityAt`, an armed watchdog fires `onTimeout()` once `idleMs >= timeoutMs`; used by channel transport owners to detect a stalled (not necessarily closed) connection and trigger their own recovery callback.
- No evidence found of a bare, unhandled `.send()` on a null socket comment/crash-note equivalent to Empyralis's `ws-client.ts:700-711` — not confirmed absent, only not found by the auditing sub-agent within the files it read.

## 2. Process supervision

### Empyralis

- No launchd `.plist`, no pm2 config, and no gateway-specific systemd unit file exist in the repo as checked-in artifacts (repo-wide `find`; only non-gateway `.service` files exist under `deploy/`).
- The gateway's systemd unit is generated at install time by `scripts/install-agent-computer.sh:384-433` (`write_systemd_units()`): `Type=simple`, `Restart=always` (`:400`), `RestartSec=5` (`:401`), plus sandboxing directives (`:404-425`).
- `install-agent-computer.sh:474-484` (`start_without_systemd()`) explicitly warns: *"WARNING: systemd is not active; using direct process fallback... For production deployments, systemd is REQUIRED."* — outside systemd there is no restart-on-crash supervision at all.
- No macOS launchd job is wired up by any installer in the repo, per an explicit comment: *"No macOS launchd job is wired up by any installer in this repo today (confirmed: no .plist, no launchd label anywhere in scripts/)... self-update on today's macOS gateways always takes the unsupervised path"* (`empyralis-gateway/src/update/gateway-restart-handoff.ts:61-66`).
- `empyralis-gateway/src/runtime/service-mode.ts` (21 lines total) contains no watchdog/restart logic — only env-flag readers for desktop-bridge mode classification.
- `empyralis-gateway/src/index.ts`: has a single-instance PID lock (`index.ts:38-78`), SIGINT/SIGTERM → graceful `cleanup()` + `process.exit(0)` (`index.ts:249-264`), and a top-level `main().catch()` that on startup error sets `process.exitCode = 1` (`index.ts:301-305`) — **no retry, no self-restart**. Process resurrection depends entirely on whatever external supervisor is present.
- **No in-process watchdog and no self-restart-on-crash logic exists anywhere in `empyralis-gateway/src/`.**

### OpenClaw

- `src/infra/supervisor-markers.ts:11-20` defines `SUPERVISOR_HINT_ENV_VARS` (env vars whose presence implies external supervision: `LAUNCH_JOB_LABEL`, `XPC_SERVICE_NAME`, `OPENCLAW_LAUNCHD_LABEL`, `OPENCLAW_SYSTEMD_UNIT`, `INVOCATION_ID`, `SYSTEMD_EXEC_PID`, `JOURNAL_STREAM`, `OPENCLAW_WINDOWS_TASK_NAME`, `OPENCLAW_SERVICE_MARKER`, `OPENCLAW_SERVICE_KIND`); `detectRespawnSupervisor()` (`:54-80`) returns `"launchd" | "systemd" | "schtasks" | null`. This is a single source of truth consumed by `src/infra/process-respawn.ts`, `src/infra/update-managed-service-handoff.ts`, `src/gateway/server-methods/update.ts`, and `src/cli/gateway-cli/run.ts:971`.
- No internal crash-loop/restart-on-crash loop exists in `src/cli/gateway-cli/run.ts` or `run-loop.ts` either — `run.ts` starts the gateway once per invocation; restart-after-crash is delegated to the OS supervisor when one is detected. `restartGatewayProcessWithFreshPid()`/`respawnGatewayProcessForUpdate()` (`src/infra/process-respawn.ts:67-108,118-148`) check `detectRespawnSupervisor()` first: if supervised, they return `{mode:"supervised"}` and the caller **exits cleanly, letting the supervisor relaunch** (comment: *"On macOS launchd, exit cleanly and let KeepAlive relaunch the service... Avoid detached kickstart/start handoffs here so restart timing stays tied to launchd's native supervision"*, `process-respawn.ts:75-77`). If unsupervised, falls back to `{mode:"disabled"}` (in-process restart) except for update respawns on unmanaged Windows.
- If a spawned/updated child never becomes healthy, the code falls back to an **in-process restart** (same PID) rather than a crash-loop retry (`src/cli/gateway-cli/run-loop.ts:174-320`, specifically `:186-220`), verified via `waitForHealthyChild()` before handoff completes.
- Crash-loop **detection** (not initiation) exists: `isSystemdStartLimitHit()` (`src/daemon/service-runtime.ts:121-141`) detects when systemd itself has exhausted `StartLimitBurst`, surfaced via doctor/status rather than acted on directly.
- **Managed-service install/repair is itself part of the doctor flow**: `maybeRepairGatewayDaemon()` (`src/commands/doctor-gateway-daemon-flow.ts:187-505`) interactively offers to install a missing service, restart a stopped one, or repair an un-loaded LaunchAgent, gated by whether the service is externally managed. `maybeRepairGatewayServiceConfig()` (`src/commands/doctor-gateway-services.ts:400-693`) audits the *installed* systemd unit/launchd plist/Windows Scheduled Task definition against the expected plan (entrypoint drift, stale token env, Bun→Node migration, PATH drift) and can repair it.
- Post-restart health is proven via `waitForGatewayHealthyRestart()` (`src/cli/daemon-cli/restart-health.ts:517-585`): polls up to 120 attempts at 500ms (60s total, `:22-26`), checking port + service-runtime + WebSocket reachability (`confirmGatewayReachable()`, `:238-267`) and cross-checking the listening PID is actually owned by the service-reported runtime PID (`:84-89`) to catch stale/orphaned listeners.

**Delta**: Both systems ultimately rely on the OS supervisor (systemd/launchd `Restart=always`/`KeepAlive`) for crash recovery — neither has a true in-process crash-loop restart. The difference is everything *around* that reliance: OpenClaw has a `doctor` flow that can detect and install/repair a missing or misconfigured service unit, verifies post-restart health with a bounded poll loop cross-checking PID ownership, and centralizes supervisor detection in one module consumed by ~4+ call sites. Empyralis has none of that — the systemd unit is written once by the install script and never audited/repaired afterward, and there is no post-restart health verification step anywhere in the gateway's own code.

## 3. Heartbeats

### Empyralis

- `HeartbeatLoop.start()` (`empyralis-gateway/src/cloud/heartbeat.ts:27-89`) uses chained `setTimeout` (not `setInterval`), interval floored at 1000ms (`:30`).
- Actual interval comes from the backend session: `session.heartbeat_interval_seconds * 1000` passed at `ws-client.ts:306-326`. Local fallback default `heartbeatIntervalMs = 20_000` (`empyralis-gateway/src/config.ts:144`).
- Each tick races `sendHeartbeat()` against a timeout (`heartbeat.ts:52-59`); `maxConsecutiveFailures` defaults to 3 in the loop (`heartbeat.ts:32`) but the gateway overrides it to **2** at the call site (`ws-client.ts:309`) — after 2 consecutive heartbeat failures the socket is force-terminated (`ws-client.ts:317-318`).
- `buildGatewayHeartbeatPayload()` (`empyralis-gateway/src/cloud/heartbeat-payload.ts:12-29`) sends: `health_state` (hardcoded literal `"online"`, `:14` — always sent as `"online"` regardless of actual local state), `journal_cursor`, `checkpoint_cursor`, `queue_depth_summary`, `capability_readiness` (requested/ready/blocked/permission_states/passive_services/service_statuses), `service_inventory`, `native_runtime`.
- Backend (`server_modules/gateway_health_service.py`) freshness/staleness thresholds: `heartbeat_fresh = heartbeat_age <= 45` seconds (`:424,430`); `stale_ws = heartbeat_age > 15*60` (15 min, `:676`), with a 5-minute warn tier (`:679`). Overall status derivation (`:444-451`): `blocked` if registration inactive/untrusted → `offline` if not session-connected → `degraded` if `reported_health=="degraded"` or heartbeat not fresh → else `healthy`.

### OpenClaw

- No dedicated heartbeat-loop equivalent was found by the auditing sub-agent in the files it read (scope was reliability/watchdog infra, not the heartbeat transport itself) — OpenClaw's "heartbeat" concept found in this audit relates to **agent session heartbeats** (synthetic recurring turns to a configured agent session), not gateway-liveness heartbeats: `src/infra/heartbeat-wake.ts` exists (not read in full) and doctor has three dedicated modules for repairing heartbeat-related state corruption: `doctor-heartbeat-main-session-repair.ts`, `doctor-heartbeat-session-target.ts`, `doctor-heartbeat-template-repair.ts` (see §5 below). This audit did not find an OpenClaw equivalent of Empyralis's cloud-connection heartbeat loop/payload — OpenClaw's gateway health model in the files read is built on RPC probes (`gateway.status`, `channels.status`) rather than a periodic heartbeat frame.

## 4. Health reporting

### Empyralis

- `collectPassiveInventorySnapshot()` (`empyralis-gateway/src/health/service-inventory.ts:704-793`) probes in parallel: Postgres, Docker, Ollama, Codex CLI, Claude Code CLI, GPU — each yielding a status of `ready|degraded|offline|missing|unknown|blocked`. Cached in-process for 60s (`PASSIVE_INVENTORY_CACHE_TTL_MS`, `:86`).
- Docker probe gates `shell_sandbox` permission (`:738-739`); Ollama/CLI probes gate `llm_runtime` (`:740-755`).
- `capability_readiness.ready`/`.blocked` are recomputed every heartbeat tick (`:771-772`, `applyLocalRunnerReadiness` at `:274-304`) — but only over the fixed `requested` capability list computed once at startup (see §5).
- `service-inventory.ts:399-434` documents that on-box permission checks for local desktop-control capabilities are hardcoded to `false` — "ARCHIVED (Phase U1)" — because the Rust supervisor daemon that implemented desktop control no longer exists (also `ws-client.ts:429-434`).
- `health_state` is sent hardcoded `"online"` in the heartbeat payload (`heartbeat-payload.ts:14`) even though the client tracks real nuance (`"degraded"`, `"reconnecting"`, `"offline"`) locally via `GatewayCheckpoints.saveHealthState()` calls throughout `ws-client.ts` (e.g. `:312,322,372,386,423,540,775,887`) — that nuance is not what's transmitted in the heartbeat frame itself.
- `personal_channel_health` is computed backend-side by `_summarize_personal_channel_health()` (`server_modules/gateway_health_service.py:347-394`); client-side a similarly-named field is published separately via `PersonalChannelRuntimeRegistry.publishRegistryState()` (`empyralis-gateway/src/channels/personal-runtime.ts:218-228`) as part of `gateway.state.update`, not the heartbeat frame.
- A backend "doctor" HTTP endpoint exists: `GET /gateway/registrations/{gateway_id}/doctor` (`server_modules/routes_gateway.py:3639-3677`) → `gateway_doctor_payload()` (`server_modules/gateway_health_service.py:397-775`), aggregating registration/device-trust/session/heartbeat-freshness/checkpoint-resume/passive-inventory/pending-approvals/personal-channel/browser/provider-reachability/workspace-quota/outbox-backlog/database-health/stale-websocket checks — entirely backend-driven against stored state plus live provider probes; not run from or exposed by the gateway process itself, and gated behind workspace-viewer-role API-key auth.

### OpenClaw

- `checkGatewayHealth()` (`src/commands/doctor-gateway-health.ts:67-145`): calls gateway RPC `status` (10s timeout), probes `channels.status` with `probe:true` for per-channel warnings (`:85-104`); a credentials-required error falls back to pre-auth `probeGatewayStatus()` — a reachable-but-unauthenticated gateway is reported as `healthOk:true, authenticated:false` (`:109-127`) rather than simply "down." Also warns on CLI/gateway version skew (`noteCliGatewayVersionSkew`, `:46-59`). Read-only in this file; no repair performed here.
- `probeGatewayMemoryStatus()` (`doctor-gateway-health.ts:148-192`) probes `doctor.memory.status` RPC, distinguishing a gateway-intentional skip from a transport timeout.

## 5. Capability advertising

### Empyralis

- `supportedCapabilities()` (`empyralis-gateway/src/supervisor/capability-router.ts:70-91`) aggregates capabilities from browser runtime, personal-channel runtimes, external-agent-proxy, shell-sandbox (Docker-gated), LLM runtime (Ollama-gated), CLI-setup runtime, and self-update runtime (unconditional — comment at `:58-66` states self-update is deliberately never permission-gated locally; safety lives in backend role-gating).
- **Computed once at startup, never recomputed**: the only production call site of `supportedCapabilities()` is `empyralis-gateway/src/index.ts:211`, inside `buildRuntimeMetadata()`, executed once in `main()` before `client.run()` is ever called. `runtimeMetadata` is built once (`index.ts:209-212`) and passed by reference into the infinite reconnect loop (`index.ts:285`) — the loop never rebuilds it.
- Explicit comment confirming this design: *"requestedCapabilities is computed exactly once at startup and never recomputed for this process's lifetime (heartbeats only re-evaluate ready/blocked within that fixed list)... so this probe MUST be awaited here, before that one-time computation, or a Docker daemon that's genuinely available could still be wrongly excluded for the whole life of this process"* (`index.ts:159-166`).
- Practical effect: a capability that becomes available after startup (e.g., Docker installed post-launch) is never *added* to what's advertised without a full process restart — only ready/blocked status *within* the original requested list is re-evaluated each heartbeat.
- `personalChannelsEnabled` gate: declared `empyralis-gateway/src/config.ts:11`, loaded `personalChannelsEnabled: normalizeBoolean(env.EMPYRALIS_GATEWAY_PERSONAL_CHANNELS_ENABLED, false)` — **defaults to `false`** (`config.ts:147`). Consumed at `index.ts:150-158`: when false, `PersonalChannelRuntimeRegistry` is constructed with an empty runtime array — WhatsApp/Telegram/local-bridge channels (iMessage, Signal, WeChat, etc.) are entirely absent from capability advertising when this flag is off.

### OpenClaw

- No direct equivalent of a single "compute capabilities once at startup" function was investigated in this audit (out of the sub-agent's assigned scope). Relevant to this section: OpenClaw's per-channel transport has its own auto-restart policy (`CHANNEL_RESTART_POLICY`, §1) rather than a single static capability-readiness snapshot taken once at process start.

## 6. Self-update

### Empyralis

Files: `gateway-self-update-runtime.ts` (249 lines), `gateway-restart-handoff.ts` (264 lines), `gateway-artifact-installer.ts` (309 lines), `gateway-release-layout.ts` (73 lines), `gateway-version-compare.ts` (43 lines).

- Backend dispatches `gateway.self_update` as a `tool.invoke` capability over the existing WS connection (`gateway-self-update-runtime.ts:22-28`), routed through `handleCapabilityInvoke()` (`:122-237`). No-op if `target_version === currentVersion` (`:134-141`).
- `downloadGatewayArtifact()` (`gateway-artifact-installer.ts:100-151`): streams+hashes, enforces `MIN_ARTIFACT_BYTES=1024` (`:19`), verifies sha256 **only if** an explicit checksum or `<url>.sha256` sidecar is available — otherwise install proceeds with `checksumVerified:false` (`:150`). Comment: *"Absence is normal today... no publish pipeline exists yet to publish one"* (`:56-60`) — i.e. unverified installs are the expected production state today.
- Extract → `.staging-<random>` dir → validate `dist/index.js` exists → atomic rename into `releasesDir/<version>` (`gateway-artifact-installer.ts:193-245`) → atomic `current` symlink swap (`:258-273`).
- Restart handoff (`gateway-restart-handoff.ts`): if `detectGatewaySupervisor()` finds systemd/launchd (`:47-78`), schedules a clean shutdown and relies on `Restart=always`. Otherwise spawns a detached handoff script (`:220-263`) that waits for the parent PID to exit, launches the new build, and rolls back + relaunches the previous release if the new build doesn't survive an 8s health-grace window (`DEFAULT_HEALTH_GRACE_MS=8000`, `:211`). As noted in §2, the launchd detection branch has never matched a real box (no installer wires up launchd), so macOS self-updates always take the unsupervised handoff-script path (`:60-66`).
- **Documented bootstrap gap**: *"this only takes effect once something actually launches the gateway through `installRoot/current/gateway/dist/index.js`... a plain `node dist/index.js` from a fixed checkout, or the current production run-gateway script pointed at the OLD root-owned install path, will never see a swap this code makes... this runtime cannot bootstrap itself into that position from inside a capability invoke"* (`gateway-self-update-runtime.ts:54-61`) — self-update cannot activate itself on an existing install without a separate one-time launcher-path migration.
- `tool.interrupt` is explicitly unsupported for `gateway.self_update` by design (`capability-router.ts:274-288` — once download/extract starts it completes or fails atomically; no cancel path).
- No automated recovery if rollback itself has nothing to roll back to: handoff script logs *"no previous release recorded to roll back to — manual recovery is required on this box"* with no further automated action (`gateway-restart-handoff.ts:159-162`).
- No doctor/health-check pass is run as part of Empyralis's self-update flow — the only "verification" step is the 8s health-grace window before rollback in the unsupervised handoff path.

### OpenClaw

- `runGatewayUpdate()` (`src/infra/update-runner.ts:774`) is the core update engine (git-source and global-package modes), invoked by `openclaw update` CLI or the detached managed-service handoff.
- Git mode: dirty-checkout guard (`git status --porcelain`, `:949-969`, aborts on uncommitted changes) → dev-channel candidate resolution via `git rev-list --max-count=10` → **preflight build-in-worktree loop** (`:1180-1350`): builds each candidate SHA newest→oldest in an isolated `git worktree` (deps install + build + optional lint), picks the first that passes as `selectedSha`, before ever touching the real checkout. Stable/beta channels resolve the newest matching tag directly (no worktree preflight).
- Applies the selected SHA to the real repo, runs real deps/build/ui-build, then **runs `openclaw doctor --non-interactive --fix` against the new build as a gating step** (`update-runner.ts:1567-1581`, env `OPENCLAW_UPDATE_IN_PROGRESS=1`).
- Any git step failure triggers `rollbackGitCheckout()` (`:889-943`): `git reset --hard`, checkout back to original branch/SHA, delete any dev branch created.
- Global/package mode delegates to `runGlobalPackageUpdateSteps()` (`src/infra/package-update-steps.ts:564-767`): stages the install into a **separate temp npm prefix** rather than installing over the live package (`:346-379`); on install failure retries with an omit-optional-deps fallback (`:640-677`); verifies the installed version; atomically swaps staged→live via `swapStagedNpmInstall()` with **rollback on any exception during the swap itself** (moves the backup back into place, `:537-547`); only then runs the caller's `postVerifyStep` (which is where doctor `--fix` runs) — and only if verify+swap both succeeded (`:733-745`).
- **Restart sentinel** (`src/infra/restart-sentinel.ts`, SQLite table `gateway_restart_sentinel`): a persisted record carrying update/restart outcome across the process boundary so the *new* process can report success/failure back to the requesting session (`:19-146`). `finalizeUpdateRestartSentinelRunningVersion()` (`:171-191`) stamps the confirmed running version once the new process proves healthy; `markUpdateRestartSentinelFailure()` (`:193-211`) flips it to `status:"error"` if the post-restart health check fails, read by the *old* process which is still alive watching the spawn.
- **Managed-service handoff** (`src/infra/update-managed-service-handoff.ts:654-732`): spawns a detached helper that waits for the parent PID to exit, runs `openclaw update --yes --json`, and on failure runs **best-effort service recovery** — `systemctl --user start`, or `launchctl kickstart`→`enable`→`bootstrap`→`kickstart` retry chain, or `schtasks.exe /Run` (`:331-370`), invoked whenever the spawned update command fails to start, exits non-zero, or is signal-killed (`:412-431,442-448`).
- Post-restart health proof: `waitForGatewayHealthyRestart()` (`src/cli/daemon-cli/restart-health.ts:517-585`, 120 polls × 500ms) before the restart is declared successful.
- **A second, full `doctorCommand()` run happens after a confirmed-healthy restart** (`src/cli/update-cli/update-command.ts:2506`) and again inside `update finalize` (`:2670`), covering the broader check suite (config, auth, sessions, plugins, sandbox), not just the update-specific steps.
- `runPostCorePluginConvergence()` (`src/cli/update-cli/post-core-plugin-convergence.ts:96-177`) runs after core swap + doctor pass but before restart: repairs missing configured plugin installs (failures nonblocking — "an external package fetch may be transient, and failing the core update would strand the user," `:90-95`), then runs a **plugin payload smoke check** whose failure **does** set `errored:true` and blocks the restart (`:94-95,173`).
- Summary: health checks run at 4 distinct gates during a single OpenClaw update — pre-apply build preflight (git mode only), post-build/pre-restart doctor `--fix`, post-core plugin smoke check, and post-restart health-poll + a second full doctor pass.

## 7. Doctor / diagnostic / preflight

### Empyralis

- **No CLI subcommand** (`doctor`, `preflight`, `self-check`, `diagnostic`) exists anywhere in `empyralis-gateway/src/` — confirmed by repo-wide grep (no true hits) and `empyralis-gateway/package.json` (no `bin` entry, no such npm script; only `build`, `typecheck`, `test`, `dev:bridge`, `signal:bridge`).
- The only "doctor" concept in the whole system is the backend-side, read-only HTTP endpoint `GET /gateway/registrations/{gateway_id}/doctor` (`server_modules/routes_gateway.py:3639-3677` → `server_modules/gateway_health_service.py:397-775`) described in §4 — it aggregates stored state and live provider probes server-side; it is not invoked by, exposed by, or runnable from the gateway process itself, has no `--fix`/repair mode, and is gated behind workspace-viewer-role API-key auth.

### OpenClaw

- `openclaw doctor` is a first-class CLI command (`src/commands/doctor.ts:7-27` entry point → `src/flows/doctor-health.ts:21-102` full interactive flow), backed by a `HealthCheck` contract (`src/flows/health-checks.ts:1-115`: `{id, kind, description, detect(ctx,scope)→findings, repair?(ctx,findings)→result}`, findings carry `severity: info|warning|error`) registered in a process-local registry (`src/flows/health-check-registry.ts:1-51`, collision-checked, reserves `core/doctor/` id-space from plugins).
- `runDoctorHealthRepairs()` (`src/flows/doctor-repair-flow.ts:41-84`) threads the (possibly mutated) config sequentially through every registered check, and **re-runs detect in a scoped validation pass after each repair** to confirm the repair actually cleared the finding (`:293-300`), recording a `"<id> repair left N finding(s)"` warning if not (`:149-157,244-247`).
- Interactive-vs-automatic is explicit and centrally governed: `resolveDoctorRepairMode()` (`src/commands/doctor-repair-mode.ts:14-31`) — `nonInteractive = requestedNonInteractive || (!isTty && !yes)`; `shouldAutoApproveDoctorFix()` (`:39-56`) only auto-approves with `--repair`/`--fix`/`--yes`, and explicitly suppresses auto-approval during an in-progress unattended update unless `--force` is also passed.
- **Breadth**: ~142 non-test doctor-related source files total (58 directly under `src/commands/doctor-*.ts`, 84 under `src/commands/doctor/`), covering: gateway/daemon service install+repair (`doctor-gateway-daemon-flow.ts`, `doctor-gateway-services.ts`), gateway RPC health probing (`doctor-gateway-health.ts`), heartbeat/session corruption repair (3 files), auth/OAuth profile repair (5 files), config migration/legacy-compat (~60 `shared/` modules), plugin manifest/registry repair, sandbox, security, session locks/snapshots/transcripts, skills, state-integrity/migrations, workspace status, disk space, browser, Claude/Codex CLI checks, cron store migrations, and channel-specific doctor logic.
- Example of a specific repair module: `repairHeartbeatPoisonedMainSession()` (`src/commands/doctor-heartbeat-main-session-repair.ts:252-337`) detects a main session that received only synthetic heartbeat turns and never real human interaction, and — only after an interactive confirm prompt — moves it to a fresh session key inside a concurrency-safe store transaction.
- Auto-invocation: **not run on gateway startup or on a schedule** (confirmed via grep across `src/gateway/server.ts`, `src/daemon/*.ts`, `src/cron`). **It is run automatically, unconditionally, as a gating step of every self-update** — 3 call sites, always `--non-interactive --fix`: inside `runGatewayUpdate()` git mode (`src/infra/update-runner.ts:1568`), inside the global-package `postVerifyStep` from `runGatewayUpdate()` (`update-runner.ts:1708`), and inside the CLI's own `postVerifyStep` (`src/cli/update-cli/update-command.ts:1687`). Additionally run as a direct function call (not a subprocess) after a confirmed-healthy post-update restart (`update-command.ts:2506`) and inside `update finalize` (`update-command.ts:2670`).
