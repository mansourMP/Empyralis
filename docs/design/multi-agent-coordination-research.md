# Multi-agent coordination and long-horizon scope control — research report

Scope: live official sources fetched 2026-07-24. Every claim below is traced to a fetched URL. Two founder questions drove the research:

- (A) With ~20 agents in a project, how do they address each other reliably — name or ID?
- (B) How do the masters keep a long-horizon task from running off-scope, using the agent's own reasoning rather than a hard approval gate?

---

## The direct answers (a-e)

### a. Name vs ID — what do the masters actually use, and is the founder right?

The founder is right that **ID is the reliable primitive**, but every product studied layers a **name on top of the ID for display and for the LLM to address by**, not instead of it. The clearest evidence is Claude Code's own agent-teams design, which had to solve the founder's exact problem:

- Claude Code subagents are identified by a `name` frontmatter field, and the docs warn about the ambiguity risk directly: "Keep `name` values unique across the whole tree: if two files... declare the same name, Claude Code loads only one of them, chosen by filesystem read order rather than a documented precedence." (`/docs/en/sub-agents`)
- For **spawned runtime instances**, Claude Code maintains both a name (used in conversation, in `SendMessage`'s `to` field, shown in the "sibling roster") and an underlying agent ID. It explicitly documents the collision and staleness case: "`SendMessage` checks that a name still refers to the same agent it reached earlier in the conversation. If a newer agent has taken the name, such as a re-spawned background agent that reused it, Claude Code refuses the send rather than delivering it to the wrong agent... To reach the earlier agent while it's still running, Claude addresses it by the agent ID it received when it spawned that agent." (`/docs/en/sub-agents`)
- Agent-teams config stores both: "The team config contains a `members` array with each member's name and agent ID." (`/docs/en/agent-teams`)
- The **hallucination risk is closed by construction, not by validation**: the model is never asked to free-type an arbitrary name or ID. It is shown a bounded, closed list — the "sibling roster: a system reminder listing `main` and every other named agent in the session, each a valid `to` value for `SendMessage`" (`/docs/en/sub-agents`) — and it picks from that enumerated set. This is Claude Code's version of Slack's `<@U123>` / Linear's `@mention` display-vs-reference split: the roster is the directory, the ID is the reference, the name is the label a human or model reads.
- OpenAI Agents SDK handoffs work the same way structurally, at compile time rather than runtime: the target agent is a real Python **object reference** — `handoffs=[billing_agent, handoff(refund_agent)]` — not a string the model invents. The model only ever sees a tool named `transfer_to_<agent_name>`, generated from that object at build time, so the LLM is choosing among a small, developer-fixed tool list, never typing a free-form identifier. (`openai.github.io/openai-agents-python/handoffs/`)
- AutoGen and CrewAI, by contrast, have **no separate ID system at all** — agents are addressed purely by the name string passed at construction (`AssistantAgent("primary", ...)`, `source='primary'` in AutoGen; `role`/filename in CrewAI). (`microsoft.github.io/autogen/.../teams.html`, `docs.crewai.com/concepts/agents`) Neither framework is designed for the founder's "20 agents, long-running, get renamed/resumed" scenario — they assume a small, short-lived, developer-defined set of agents in one process, so the ambiguity/mutability problem the founder is worried about never comes up in their docs.

**Conclusion: only the product built for the founder's actual scale (many agents, long sessions, resumable, renamable) had to invent the ID-with-name-alias pattern — which is exactly what the founder is proposing.** Name-only addressing (AutoGen, CrewAI, OpenAI's compile-time object references) works only because those systems keep the agent set small, static, and developer-defined; it stops working the moment agents are dynamically spawned, renamed, or resumed across a long session, which is precisely the founder's "20 agents in a project" case.

### b. Auto-naming — does any product do it, and how?

Yes, and it splits into two distinct mechanisms, both live in Claude Code:

1. **Model-generated display names for sessions/tasks.** Claude Code background sessions: "Display Name: Auto-generated from the prompt by a Haiku-class model, customizable with `--name` flag... Ctrl+R... `/rename`." (`/docs/en/agent-view`) Codex's cloud task list shows the same pattern from the outside — task titles are described as auto-generated from the task/work description, with an open community request (`openai/codex` issue #12564) to make them renamable, and issue #17782 asking for custom session IDs at launch — confirming Codex's canonical session identifier is an opaque UUID, not a human name, and that naming is a UI-layer add-on, not a core addressing primitive. (`developers.openai.com/codex/cli` → `learn.chatgpt.com/docs/codex/cli`; GitHub issue search)
2. **Orchestrator-assigned names at spawn time** — closer to what the founder recalls from Codex ("self-named"). In Claude Code agent teams: "The lead assigns every teammate a name when it spawns them, and any teammate can message any other by that name. To get predictable names you can reference in later prompts, tell the lead what to call each teammate in your spawn instruction." (`/docs/en/agent-teams`) Codex's newer subagent system requires an explicit `name` field in a TOML config as "the source of truth," plus a recent "nicknames" feature added specifically because parallel subagent threads were hard to tell apart in the picker UI — a direct, shipped acknowledgment of the founder's exact pain point. (`learn.chatgpt.com/docs/agent-configuration/subagents`; GitHub changelog search result)

AutoGen and CrewAI show no evidence of either mechanism in their official docs — names are always developer-supplied at construction time.

### c. Message-storm / cycle prevention — the convergent answer

Every framework that allows more than one agent to interact bakes in an explicit, **configurable numeric ceiling**, plus at least one semantic completion signal. None rely on the agents' own judgment alone to stop:

- **Claude Code**: three independent caps — total subagents per session (default 200, `CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION`), concurrent subagents (default 20, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`), and nesting depth, which is **zero by default** — "By default, a subagent can't spawn subagents of its own" — and must be explicitly raised via `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`. (`/docs/en/sub-agents`) Auto mode adds a parallel circuit breaker: "If the classifier blocks an action 3 times in a row or 20 times total, auto mode pauses." (`/docs/en/permission-modes`)
- **OpenAI Agents SDK**: a single `max_turns` parameter on `Runner.run`, after which it "raise[s] a `MaxTurnsExceeded` exception... It indicates that the agent could not complete its task within the specified number of interaction turns." (`openai.github.io/openai-agents-python/running_agents/`)
- **AutoGen** has the richest toolkit, because it's the one framework designed for genuinely open-ended multi-agent chat: `MaxMessageTermination`, `TokenUsageTermination`, `TimeoutTermination`, `HandoffTermination`, `SourceMatchTermination`, `ExternalTermination`, `StopMessageTermination`, `TextMessageTermination`, `FunctionCallTermination`, `FunctionalTermination` — combinable with AND/OR ("stops when *either* condition triggers" / "stops only when *both* conditions are satisfied"). The docs are explicit about why: "a run can go on forever" without one. (`microsoft.github.io/autogen/stable/.../termination.html`)
- **CrewAI** bounds the individual agent's own loop rather than a team-wide message count: `max_iter` (default 20, "Maximum iterations before the agent must provide its best answer"), `max_execution_time`, `max_rpm`, `max_retry_limit` (default 2), `max_reasoning_attempts` (unlimited if unset — "will try until ready"). (`docs.crewai.com/concepts/agents`) No team-wide termination condition is documented in the official Processes page.

### d. Hierarchical vs peer-to-peer — what the evidence actually shows

The convergent, production-hardened pattern is **hierarchical: orchestrator delegates, worker returns a summary, orchestrator synthesizes.** Free peer-to-peer messaging among many agents exists, but only as a narrow, opt-in, flat exception — never as the default, and never at the founder's "20 agents" scale:

- **Anthropic's production research system is strictly hierarchical**, and got there partly by moving *away* from looser coordination: early iterations exhibited "distracting each other with excessive updates" as a named failure mode they fixed. The shipped architecture has "a lead agent [that] coordinates the process while delegating to specialized subagents that operate in parallel," each returning findings only to the lead, which "synthesizes these results." (`anthropic.com/engineering/multi-agent-research-system`)
- **Claude Code subagents** (the default, non-experimental path): "Subagents only report results back to the main agent and never talk to each other." (`/docs/en/agent-teams`, comparison table)
- **Claude Code agent teams** is the one true peer-to-peer system found in any of these products — "teammates message each other directly" by name via a mailbox — but it is: (1) experimental and **disabled by default**, requiring `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`; (2) explicitly bounded — "Start with 3-5 teammates for most workflows... Scale up only when the work genuinely benefits... Three focused teammates often outperform five scattered ones"; (3) flat, not nested — "No nested teams: teammates cannot spawn their own teammates. Only the lead can manage the team"; and (4) still centrally spawned and permission-gated by one fixed lead — "Lead is fixed: the main session is the lead for its lifetime. You can't promote a teammate to lead or transfer leadership." (`/docs/en/agent-teams`)
- **OpenAI Agents SDK's "decentralized" pattern is not free messaging either** — a handoff is "a one way transfer," and once triggered "the new agent takes over the conversation" — there is no return channel, no simultaneous N-way chat, just a single hot-potato hand-off. The alternative, "manager" pattern, is explicitly hierarchical: "a central manager/orchestrator invokes specialized sub-agents as tools and retains control." (`openai.github.io/openai-agents-python/multi_agent/`, `.../handoffs/`)
- **AutoGen** is the genuine outlier — `RoundRobinGroupChat`/`SelectorGroupChat` broadcast every message to every agent — but even there only one agent speaks per turn (chosen by rotation or a selector model), and it is a research/orchestration library, not a pattern either Anthropic or OpenAI adopted for their own flagship coding-agent products.
- **CrewAI** documents only sequential and hierarchical-manager processes; no peer-broadcast pattern appears in the official docs at all.

**For "20 agents in a project": no source studied recommends, or even supports, a flat mesh at that scale.** The one framework with real peer messaging (Claude Code agent teams) caps its own recommendation at 3-5 before "coordination overhead increases" and "diminishing returns" set in, and keeps addressing scoped to a single flat team under one lead. At 20 agents, the convergent recommendation from every source is a tree — one or more layers of orchestrators — not a mesh where any agent messages any other by name or ID.

### e. Long-horizon guardrails that live in the agent's reasoning, not a hard gate

The founder's constraint (no approval system) rules out permission dialogs as the mechanism. The pattern that recurs across Anthropic's and OpenAI's own guidance is not "add a gate" but **"give the agent something checkable to point at as evidence of done, and make halting-on-failure part of what an agent even is."**

- **Externalize the plan into a checkable list.** Claude Code's Task/TodoWrite tools give the model a structured list with exactly three states (pending / in_progress / completed); the model itself decides when an item flips state, but "done" becomes "the list is empty," not a vibe. (`/docs/en/agent-sdk/todo-tracking`)
- **Plan before touching anything, without a stop-and-ask loop.** Plan mode: "Claude reads files, runs shell commands to explore, and writes a plan, but does not edit your source," and `auto` mode is explicitly designed to avoid interrupting: "a background classifier reviews commands... Boundaries you state in conversation" are re-read from the transcript on every check rather than requiring a fresh approval each time. (`/docs/en/permission-modes`)
- **Persisted, self-authored notes as the memory mechanism for staying on track.** Anthropic's context-engineering guidance: "Structured note-taking, or agentic memory, is a technique where the agent regularly writes notes persisted to memory outside of the context window," letting it "track progress across complex tasks, maintaining critical context and dependencies that would otherwise be lost." (`anthropic.com/engineering/effective-context-engineering-for-ai-agents`)
- **Bound context per sub-task so drift can't compound.** The same post: "Sub-agent architectures provide another way around context limitations. Rather than one agent attempting to maintain state across an entire project, specialized sub-agents can handle focused tasks with clean context windows," each returning "only a condensed, distilled summary of its work (often 1,000-2,000 tokens)." A subagent physically cannot flood the parent with scope creep because only the summary crosses the boundary. (same source)
- **Make "recognize done / self-correct / halt on failure" part of the definition of an agent, not an add-on.** OpenAI's guide states this as characteristic #1 of what an agent *is*: "It recognizes when a workflow is complete and can proactively correct its actions if needed. In case of failure, it can halt execution and transfer control back to the user." (`cdn.openai.com/.../a-practical-guide-to-building-agents.pdf`, p.4) The "run" concept underneath every orchestration pattern is a loop with an exit condition that can be semantic — "a final-output tool is invoked" — as well as numeric — "reaching a maximum number of turns" (p.14-15) — and both coexist rather than one replacing the other.
- **Reserve hard stops for two named categories only, not general checkpoints.** The same guide scopes human intervention narrowly: "Exceeding failure thresholds: Set limits on agent retries or actions... High-risk actions: Actions that are sensitive, irreversible, or have high stakes should trigger human oversight." (p.31) This is the opposite of a blanket approval gate — it is a short, explicit exception list, with everything else running on the agent's own judgment of completion.

Read together, these sources describe the founder's Codex failure ("built work that was stupid, kept going because I told it not to stop") as a violation of a documented first principle, not an edge case: an agent that has no checkable list, no persisted notes on why it's still working, and no self-recognized completion condition — running only on "don't stop" — is missing exactly the three properties OpenAI's own definition of an agent requires.

## Per-product mechanics (cited)

### Claude Code sub-agents
Identity is set entirely by the `name` frontmatter field: "identity comes only from the `name` frontmatter field," and duplicate names within a directory resolve by filesystem read order (undocumented precedence) or, across nested project directories, by proximity to the working directory. (`/docs/en/sub-agents`)

A subagent starts with a fresh, isolated context window — no conversation history, no already-read files — and only "the system prompt that guides the subagent's behavior" plus a delegation message Claude writes; only its final summary returns to the caller. Foreground subagents block the caller; background subagents (the default since v2.1.198) run concurrently and surface permission prompts back in the main session, naming which subagent is asking. Explicit invocation is by natural language, `@-mention` (`@agent-<name>`), or `--agent <name>` for the whole session. Resuming an existing subagent instance is done via `SendMessage` with either its name or its agent ID — with the name path validated against staleness as detailed in answer (a). Nesting (a subagent spawning its own subagents) is off by default and capped by `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` when enabled. Claude Code also scans every subagent's final report for prompt-injection-shaped text before the parent reads it — "the scan inserts a backslash into text that imitates Claude Code's own output... [or] prepends a line... `[harness: subagent output matched instruction-shaped pattern(s):`" — a defense specifically against a subagent's tool results carrying hostile instructions back up the hierarchy. (`code.claude.com/docs/en/sub-agents`)

### Claude Code agent teams (experimental)
The only peer-to-peer messaging system found in the research: a shared task list, a per-agent mailbox (`~/.claude/teams/{team-name}/inboxes/{agent-name}.json`), and direct name-addressed messaging, with the lead spawning and naming every teammate and remaining fixed for the session's lifetime. Explicitly bounded to 3-5 teammates as the practical sweet spot, one flat layer (no nested teams), and off by default behind `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`. A teammate cannot approve a permission prompt on the user's behalf, and "a teammate that was denied an action cannot relay it to another teammate to bypass the check." (`code.claude.com/docs/en/agent-teams`)

### Claude Code background agents / agent view
Every background session gets a short filesystem ID, a full UUID, and an auto-generated display name from "a Haiku-class model," renamable via `--name`, `Ctrl+R`, or `/rename`. Monitoring is via a status-icon list (`claude agents`), a "peek" panel that shows the exact blocking question or result without attaching, and full attach for the complete transcript. `claude agents --json` exposes machine-readable state per session (`id`, `state`, `sessionId`, `name`). (`code.claude.com/docs/en/agent-view`)

### Anthropic — "How we built our multi-agent research system"
Architecture: "a lead agent coordinates the process while delegating to specialized subagents that operate in parallel." Each subagent is given "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries" and "return[s] a list of companies to the lead agent so it can compile a final answer" — condensed findings, not full transcripts. Reported cost: "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats." Documented failure modes from early iterations: "spawning 50 subagents for simple queries, scouring the web endlessly for nonexistent sources, and distracting each other with excessive updates," plus "agents continuing when they already had sufficient results" and subagents duplicating each other's searches. Explicit scope limit on when multi-agent is the wrong choice: "some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit for multi-agent systems today. For instance, most coding tasks involve fewer truly parallelizable tasks than research." (`anthropic.com/engineering/multi-agent-research-system`)

### Anthropic — "When and how to use multi-agent systems" (Claude blog)
Reinforces the same cost finding independently: "Multi-agent implementations typically use 3-10x more tokens than single-agent approaches for equivalent tasks," and warns of a specific organizational failure pattern: "Teams invest months building elaborate multi-agent architectures only to discover that improved prompting on a single agent achieved equivalent results." Prescribes starting single-agent and adding agents only for three reasons: context pollution, genuinely parallelizable work, or specialization needs. (`claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them`)

### Anthropic — "Effective context engineering for AI agents"
Frames long-horizon coherence as a context-budget problem: "Long-horizon tasks require agents to maintain coherence, context, and goal-directed behavior over sequences of actions where the token count exceeds the LLM's context window." Names three mitigations: compaction ("summarizing [the conversation] and reinitiating a new context window with the summary"), structured note-taking/agentic memory (persisted outside the context window), and sub-agent architectures with condensed 1,000-2,000 token summaries returning to the parent. General principle: find "the smallest set of high-signal tokens that maximize the likelihood of your desired outcome." (`anthropic.com/engineering/effective-context-engineering-for-ai-agents`)

### Claude Code — permission modes / plan mode / auto mode
Plan mode restricts to read-only tools until a plan is approved. Auto mode is the closest thing to "guardrails in reasoning, not a gate": a background classifier evaluates every action against a fixed, versioned rule set (data exfiltration, production deploys, force pushes, secret handling, etc. — dozens of named categories) rather than prompting per action; user-stated boundaries ("don't push") are re-read from the transcript on each check rather than stored as a rule, and are lost if compaction removes the message that stated them — a real, documented limitation. A 3-in-a-row or 20-total block count causes auto mode to fall back to prompting. Subagent actions are checked at spawn (task description), during execution (same rules as parent), and again on return (full action-history review). (`code.claude.com/docs/en/permission-modes`)

### Claude Code — Todo/Task tools
The SDK maintains a structured, three-state task list (`pending` / `in_progress` / `completed`) via `TaskCreate`/`TaskUpdate`/`TaskGet`/`TaskList` (superseding the older single `TodoWrite` call). The model creates todos for "complex multi-step tasks requiring 3 or more distinct actions" and "may skip todos for very short or single-step requests" — i.e., the decision to externalize a plan is itself left to the model's judgment, not a forced gate. (`code.claude.com/docs/en/agent-sdk/todo-tracking`)

### OpenAI Agents SDK — handoffs
A handoff's target is a real `Agent` object passed at construction (`handoffs=[billing_agent, handoff(refund_agent)]`), exposed to the model as a tool named `transfer_to_<agent_name>` by default (overridable via `tool_name_override`). Structured input to a handoff is validated locally against a Pydantic schema before an `on_handoff` callback runs. By default "the new agent takes over the conversation, and gets to see the entire previous conversation history," though an `input_filter` can transform what history the receiving agent sees. (`openai.github.io/openai-agents-python/handoffs/`)

### OpenAI Agents SDK — orchestration patterns and turn limit
Two named patterns: agents-as-tools ("Use agents as tools when a specialist should help with a bounded subtask but should not take over the user-facing conversation") and handoffs ("Use handoffs when routing itself is part of the workflow and you want the chosen specialist to own the next part of the interaction"). `Runner.run(..., max_turns=N)` raises `MaxTurnsExceeded` when the cap is hit; passing `max_turns=None` disables it. (`openai.github.io/openai-agents-python/multi_agent/`, `.../running_agents/`)

### OpenAI — "A practical guide to building agents" (PDF)
Defines an agent by three components (Model, Tools, Instructions) and, critically, by behavior: recognizing completion, self-correcting, and halting on failure (p.4). States the orchestration decision plainly: "Our general recommendation is to maximize a single agent's capabilities first... often a single agent with tools is sufficient" (p.16), splitting only for "complex logic" (too many conditional branches in one prompt) or "tool overload" (more than ~15 overlapping tools). Multi-agent splits into manager (agents-as-tools, "one agent to control workflow execution and have access to the user," p.18) and decentralized handoff ("optimal when you don't need a single agent maintaining central control," p.21) patterns — mirroring the SDK docs exactly, since the guide is written around the same SDK. Guardrails are explicitly layered ("a single one is unlikely to provide sufficient protection") across relevance classifiers, safety classifiers, PII filters, moderation, rules-based blocklists, and per-tool risk ratings (low/medium/high, by "read-only vs. write access, reversibility, required account permissions, and financial impact") that gate only high-risk calls, not all calls (p.24-27). Human intervention is scoped to exactly two triggers: exceeding a failure/retry threshold, or a high-risk/irreversible action (p.31). (`cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf`)

### Codex CLI
Canonical session identity is an opaque UUID (`codex resume <uuid>`, sessions stored as JSONL under `~/.codex/sessions/YYYY/MM/DD/`); a GitHub feature request (#17782) for a custom, human-chosen session ID at launch is still open, confirming names are not yet a first-class addressing primitive at the session level. (`developers.openai.com/codex/cli` → `learn.chatgpt.com/docs/codex/cli`; GitHub issue search)

Codex subagents are a newer, separate mechanism: three built-ins (`default`, `worker`, `explorer`) plus custom agents defined in TOML under `~/.codex/agents/` or `.codex/agents/`, each requiring a `name` field as "the source of truth." Invocation is by direct natural-language request ("spawn one agent per point"), by project/skill configuration, or — at the "Ultra" intelligence tier in ChatGPT — proactive automatic delegation. Results return as summaries, not raw output: the orchestrator "waits until all requested results are available, then returns a consolidated response." Concurrency is capped by `agents.max_concurrent_threads_per_session`. A recently shipped "nicknames" feature for the parallel-agent picker UI is a direct, shipped response to the exact addressability problem the founder describes. (`developers.openai.com/codex/concepts/subagents` → `learn.chatgpt.com/docs/agent-configuration/subagents`)

### Microsoft AutoGen
Agents are addressed purely by the name string given at construction (`AssistantAgent("primary", ...)`; messages carry `source='primary'`). `RoundRobinGroupChat` broadcasts every agent's message to the whole team and rotates the speaker deterministically; `SelectorGroupChat` instead "selects the next speaker using a ChatCompletion model after each message" — an LLM decides who talks next, not a fixed order; `Swarm` uses explicit `HandoffMessage` signals instead of broadcast. Ten-plus built-in termination conditions (`MaxMessageTermination`, `TokenUsageTermination`, `TimeoutTermination`, `HandoffTermination`, `SourceMatchTermination`, `ExternalTermination`, `StopMessageTermination`, `TextMessageTermination`, `FunctionCallTermination`, `FunctionalTermination`) are combinable with `&`/`|`, and are explicitly framed as necessary because "a run can go on forever" otherwise. (`microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html`, `.../teams.html`)

### CrewAI
Agents are identified by `role`/`goal`/`backstory` and referenced either by Python object variable or by config filename (`agents/<name>.jsonc`) — no separate unique-ID system is documented. Two processes: sequential (task N's output feeds task N+1's context) and hierarchical, where a `manager_llm` or `manager_agent` dynamically allocates tasks — "tasks are not pre-assigned; the manager allocates tasks to agents based on their capabilities." Per-agent execution limits exist (`max_iter` default 20, `max_execution_time`, `max_rpm`, `max_retry_limit` default 2, `max_reasoning_attempts` unlimited by default — "will try until ready") but no team-wide message-count or round-cap termination condition is documented in the official Processes page. (`docs.crewai.com/concepts/agents`, `docs.crewai.com/concepts/processes`)

## Convergent design

1. **Two-layer addressing, everywhere it matters at scale.** A stable, non-reused reference (object reference in OpenAI's SDK; agent ID in Claude Code) underneath a human/model-facing name, with the name resolved against a small, closed roster rather than free-typed. The founder's instinct — ID as the reliable primitive — is exactly what Claude Code's own architecture falls back to the moment a name becomes ambiguous.
2. **Hierarchical-by-default, peer-to-peer-by-exception.** Every production system studied (Anthropic's research system, Claude Code subagents, OpenAI's manager pattern) defaults to orchestrator-delegates/worker-returns. The one real peer-messaging system (Claude Code agent teams) is opt-in, flat, capped at ~3-5, and still centrally spawned by one fixed lead. Nobody ships or recommends a flat mesh at 20 agents.
3. **A hard numeric ceiling always sits underneath the reasoning layer.** `max_turns` (OpenAI), concurrent/total/depth subagent caps (Claude Code), a library's worth of termination conditions (AutoGen), or per-agent iteration/time/RPM limits (CrewAI) — every framework backstops agent judgment with a number, even the ones (Claude Code auto mode, OpenAI's guide) that otherwise emphasize letting the agent decide when it's done.
4. **Completion is made checkable, not vibed.** Structured task lists (Claude Code), a semantic exit condition alongside the numeric one (OpenAI's "final-output tool invoked" vs. "max turns"), and "recognizes when a workflow is complete" as characteristic #1 of an agent (OpenAI's guide) all convert "keep going until it feels done" into something the agent can point at as evidence.
5. **Context isolation is itself an anti-scope-creep device.** Subagents/handoffs returning only a condensed summary (1,000-2,000 tokens per Anthropic; "results return... only its final result comes back" per Claude Code docs) mean a runaway exploration cannot physically flood the parent's context and compound into runaway scope the way it can in a single flat conversation.
6. **Guardrails are named and narrow, not a blanket gate.** OpenAI's two intervention triggers (failure-threshold, high-risk-action) and Claude Code's auto-mode rule list (dozens of specifically named categories, not "ask before anything risky") both reserve human-in-the-loop for an enumerated exception list, leaving everything else to the agent's own judgment — directly compatible with the founder's "no approval system" constraint.

## What NOT to do (anti-patterns the sources warn about)

- **Don't let agents free-chat without a completion or return protocol.** Anthropic's own early prototype let subagents "distract each other with excessive updates" and kept "continuing when they already had sufficient results" — they fixed this by tightening the lead/subagent return contract, not by adding more agents. (`anthropic.com/engineering/multi-agent-research-system`)
- **Don't reach for multi-agent before proving single-agent-plus-better-prompting fails.** "Teams invest months building elaborate multi-agent architectures only to discover that improved prompting on a single agent achieved equivalent results." (`claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them`) OpenAI's guide says the same: "Our general recommendation is to maximize a single agent's capabilities first." (PDF, p.16)
- **Don't use multi-agent for tightly coupled work.** "Most coding tasks involve fewer truly parallelizable tasks than research" — multi-agent is a poor fit "for domains that require all agents to share the same context or involve many dependencies between agents." (`anthropic.com/engineering/multi-agent-research-system`)
- **Don't let a name silently resolve to the wrong live agent.** Claude Code treats this as a correctness bug worth its own guard: a stale name reference is refused outright rather than silently misdelivered. (`code.claude.com/docs/en/sub-agents`)
- **Don't let subagents nest indefinitely.** Nesting depth is zero by default in Claude Code and must be explicitly raised — unbounded recursive spawning is treated as a hazard to guard against by default, not a feature to enable by default. (`code.claude.com/docs/en/sub-agents`)
- **Don't run a multi-agent conversation without an explicit termination condition.** AutoGen's docs state plainly that "a run can go on forever" without one — the framework ships ten-plus termination-condition types precisely because free multi-agent chat has no natural stopping point. (`microsoft.github.io/autogen/.../termination.html`)
- **Don't treat "don't stop" as a substitute for a completion signal.** OpenAI's own definition of an agent requires it to "recognize when a workflow is complete" and "halt execution" on failure — an agent driven only by an instruction not to stop is, by OpenAI's own framing, missing a core property of what makes it a properly designed agent, which matches the founder's Codex failure description exactly. (PDF, p.4)
- **Don't treat guardrails or approval as a single layer.** "A single [guardrail] is unlikely to provide sufficient protection" — the guide insists on layering classifier + rules-based + tool-risk-rating checks rather than one blanket check. (PDF, p.25)
- **Don't let stated conversational boundaries be the only enforcement if they must survive compaction.** Claude Code's own docs flag this as a real gap: a user-stated boundary like "don't push" is re-read from the transcript each time and "can be lost if context compaction removes the message that stated it" — for a hard guarantee the docs recommend a stored rule instead of a stated boundary. (`code.claude.com/docs/en/permission-modes`)
