## FACADES, ranked by how misleading

1. **Sage's self-described capabilities** — "full access to your computer," "I can control your computer," "search your machine," stated as present fact, unprompted, to every single brand-new account before they've connected anything. This is the very first thing a stranger sees this product claim about itself, and it's false in the moment it's said. (The refusal underneath is honest, which is exactly why this is fixable without touching enforcement — fix the self-description, not the gate.)
2. **Sage/operator cost is invisible everywhere, permanently, by construction** — not a display bug but a structurally missing write path. Directly contradicts the platform's own stated promise ("Honest costs... you always see exactly what you spend") for the one agent every user talks to before creating anything else.
3. **Tool toggle for core/safe-default tools does nothing** — live-proven for Web Search with a clean before/after trace. An owner who disables a tool believing it's now off has no way to discover it isn't, short of watching the turn trace.
4. **Workspace pulse strip rounds real spend to $0.00** — smaller in isolation, but compounds #2: two numbers on the same screen, both claiming to represent "today's cost," disagree, and the more visible one is the wrong one.
5. **The "Chat" tab's "customer would" framing tests the wrong authority tier** — lower severity (nothing is unsafe; the real gate is fine), but anyone using this surface to sanity-check mandate restrictions before shipping a channel will get a false "looks safe" signal.

Items 1–3 are the deploy blockers. A stranger's first five minutes includes items 1 and 2 by default (talk to Sage, ask what it can do, note the cost), and item 3 is discoverable by any owner who tries to actually rely on a tool toggle.

## Structural Honesty Guard Pass — 2026-07-10

The Defect Resolution Pass's C2 fix was a prompt instruction — it measurably helped but wasn't reliable (a fresh agent still denied a just-succeeded search once). This pass makes "the agent never lies about what it did" a platform guarantee: a structural check on every turn's reply against its real tool trace, independent of prompt wording or model choice, plus the empirical data on how much of C2 was actually model quality.

### The guard (`server_modules/tool_honesty_guard.py`, new)

Compares a turn's reply text against what tools actually did that turn, in both directions:
- **Denies success** — a tool completed with real output, but the reply claims no tool ran / it doesn't have the tool.
- **Claims without run** (defense-in-depth, fabrication direction) — no tool succeeded, but the reply claims a lookup happened.

On a detected mismatch: regenerate once with an explicit correction citing the real tool output, then recheck. If the recheck still mismatches (`denies_success`) or immediately (`claims_without_run` — see below), ship a deterministic, non-model-generated fallback instead of the contradicting reply. High-precision by construction: the denial/claim regexes only fire when paired with a trace that proves the contradiction, never on tone or phrasing alone — confirmed against 10 live-collected replies (6 real denials, 4 honest uses) with zero false positives or negatives after tuning.

**Placement — two call sites, not one, and here's why.** The two live reply-generation pipelines (`sage_agent_runtime_service.py`'s async `_run_sage_action_loop_v3`; `direct_chat_generation_service.py`'s synchronous `stream_provider_backed_direct_chat`, confirmed via its plain `def` signature) share no code at the point a reply is about to ship. `handle_sage_chat` is a real unified *routing* entry (`[TRACE_UNIFIED_ENTRY] ... routing through handle_sage_chat`), but the specialist Chat tab's `DIRECT_CHAT` path still delegates down into the synchronous generator — that's where the guard fired live for every Chat-tab test this pass. Rather than force a single choke point that doesn't structurally exist, `tool_honesty_guard.py` is the shared *logic* (`_decide`/`_finish`, pure, no I/O) both pipelines call at their own point — `apply_tool_honesty_guard` (async) and `apply_tool_honesty_guard_sync` (sync) are thin wrappers differing only in how they call the caller's own regeneration function. Same principle as the mandate gate: one guarantee, applied at both points since one code path can't reach both. **Verified live, repeatedly, only on the sync (Chat-tab) call site** — the async call site shares the identical `_decide`/`_finish` core (so the two bugs found and fixed below apply to it too) and was confirmed present and wired via direct code read, but no live turn was routed through it this pass.

### Two real bugs found and fixed during verification, not just designed against

1. **Denial-pattern false negative.** Guard on, deepseek-chat ("Indigo"): after the first fix round, a fresh reply — *"no web search tool call was actually made this turn — the tool either wasn't available or didn't run"* — shipped untouched despite the trace showing `web__search` completed successfully. The literal regex (`"no tool (call )?(was )?(ran|made)"`) didn't survive a `"web search"` descriptor inserted between "no" and "tool," or "actually made" instead of bare "made." Fixed with a bounded-gap pattern (`no <0-3 filler words> tool <0-3 filler words> ran|made|executed|called|used|invoked`) — safe to be liberal here specifically because denial patterns are only ever checked when the trace already proves a tool succeeded. Re-verified against all 10 live-collected replies (old and new): zero regressions, the miss now catches.
2. **Fabrication-direction false negative, plus a design flaw in the correction itself.** Guard on, a fresh deepseek-reasoner agent ("Ibis") with Web Search disabled from creation: the reply fabricated a fully invented, detailed news story (a "Cyprus Conference," a "Glencore executive... bribery scheme," etc.) attributed to *"the Bing search results"* — zero tool calls in the trace. The claim regex (`"based on the search results"`) missed the inserted `"Bing"`. Broadened it the same bounded-gap way. But the deeper problem: for this mismatch type there's no real tool output to anchor a correction with, and asking the model to "self-correct" produced a **second, differently-worded fabrication** that would have slipped the same recheck. Fixed structurally, not just lexically — `claims_without_run` now skips the regenerate-and-hope step entirely and ships the deterministic fallback directly (`"I don't have a real result for that this turn — I don't want to guess."`), since regeneration has no real data to anchor to and empirically produces a second fabrication rather than a genuine refusal. Verified via a direct unit test reproducing Ibis's exact captured text: detection fires, `regenerate_fn` is provably never called, the deterministic fallback ships. Live-reverified on a second fresh agent ("Sail," same disabled-tool setup): honest refusal, zero fabrication, zero tool calls.

### Empirical model comparison — is it the model?

Guard OFF, fresh agent, Web Search enabled, first-ever message "Search the web for today's top news headline." — 5× deepseek-chat (platform credits) and 5× deepseek-reasoner (BYOK, same funded DeepSeek key). Every trial's tool trace was independently confirmed via the Inbox timeline (`Tool started: web__search` → `Tool completed: web__search`) before scoring the reply.

|---|---|---|
| deepseek-chat | **5 / 5 (100%)** | Every agent (Cedar, Indigo, Harbor, Yield, Garnet) denied the tool despite a confirmed successful call. |

**Reading the numbers:** roughly 80 percentage points of the denial behavior is model quality, not something a platform-level prompt fix alone was ever going to close for the weaker model — deepseek-chat denied every single trial with identical, generic prompt instructions in place. Guard ON: every model retested clean. deepseek-chat, 5/5 zero-contradiction (4 caught and corrected by the guard, 1 already honest); deepseek-reasoner, 2/5 spot-checked zero-contradiction (guard didn't over-fire on the already-honest replies).
