Status: **all three parts implemented and proven on the live server (ws-1, Postgres).**
Every proof below was re-run against the freshly-restarted backend after a

## Part A — Normalized usage metering

### Schema (one table)
`usage_events` — 17 columns, created live in Postgres:

```
id, tenant_id, workspace_id, agent_install_id, project_id, provider, model,
mode, tokens_in, tokens_out, total_tokens, usd_cost, pricing_known, run_id,
surface, metadata, created_at
```

Indexed on `(workspace_id, created_at)`, `(agent_install_id, created_at)`,
`(project_id, created_at)`.

- Owner: `server_modules/usage_events_repository.py` (new).
- `usd_cost` is computed via `pricing_registry_service.estimate_cost_usd(...)`;
  `pricing_known` records whether the provider/model was priced.
- Attribution flows through a `contextvar` (`USAGE_ATTRIBUTION`) set once per turn
  in `handle_sage_chat`, and is recorded at the universal all-payer choke point
  (`direct_chat_hosted_usage_service._record_direct_chat_transparency_usage`), so
  every LLM call in every mode records exactly one event without threading the
  attribution through the ~3000-line action loop.

### Attribution proof — two live turns, different models

| turn | agent_install_id | project_id | model | mode | in/out | usd_cost |
|---|---|---|---|---|---|---|
| Sage (master) | `ainstall_ws-1_sage` | `project_ac099faf698d44e8` | deepseek-**chat** | BYOK | 2538/1 | $0.000356 |
| Support Bot (specialist) | `ainstall_test_1` | `project_ac099faf698d44e8` | deepseek-**reasoner** | BYOK | 555/16 | $0.000082 |

Master → the workspace master install; specialist → its own install. Both carry
the right project, both `pricing_known=true`, both nonzero cost, distinct models.

### Rollup sample — `GET /api/w/ws-1/fleet/usage?scope=project&id=project_ac099faf698d44e8&period=day`

```json
{
  "ok": true, "scope": "project", "scope_id": "project_ac099faf698d44e8", "period": "day",
  "totals": {"events": 2, "tokens_in": 3093, "tokens_out": 17, "total_tokens": 3110, "usd_cost": 0.000438},
  "by_agent": [
    {"agent_install_id": "ainstall_ws-1_sage", "events": 1, "total_tokens": 2539, "usd_cost": 0.000356},
    {"agent_install_id": "ainstall_test_1",   "events": 1, "total_tokens": 571,  "usd_cost": 0.000082}
  ]
}
```

Project total ($0.000438) = sum of its two agents ($0.000356 + $0.000082).
`scope=agent` and `scope=workspace` verified as well. Buckets use
`date_trunc` per `period ∈ {day, week, month}`.

## Part B — Capability presets

`server_modules/capability_presets.py` (new): `knowledge | standard | operator`.
Presets seed install defaults (hardware, tools, model tier, subagents, context
policy). `CREATABLE = {knowledge, standard}`; `operator` is reserved.

### Knowledge-agent enforcement (live create)
Created `P5 Knowledge Verify` → DB truth:

```
hardware_access = none | subagents_enabled = false | capability_preset = knowledge
hardware_access_locked = true | model_tier = cheap
```

### Hardware-grant denial (the key safety proof)
`PATCH …/fleet/agents/<id>` `{"patch":{"hardware_access":"all"}}` on the locked
knowledge agent:

```json
{"ok": false, "error": "This is a knowledge agent — hardware access is policy-locked.
Change its capability preset (not just this field) to grant hardware."}
```

- `hardware_access` stayed `none` afterward (verified in DB).
- Ledger event written to `activity_ledger_events`:
  `action=hardware_grant_denied, status=blocked, event_class=fleet_control,
  reason=knowledge_agent_hardware_locked, requested_hardware_access=all`.

Presets are defaults, not cages: every other field remains overridable via
`fleet_configure_agent` — only a knowledge agent's hardware access is
policy-locked (changeable solely by changing the preset).

### Operator reserved (live create)
`{"capability_preset":"operator"}` →
`{"ok": false, "error": "capability_preset 'operator' is reserved (Sage-class
operator) and cannot be created through the normal flow. Use 'knowledge' or
'standard'."}`

## Part C — Per-agent context policy

Per-install `context_policy = {max_context_tokens, on_context_full}` where
`on_context_full ∈ {compact, fresh_session}`, defaulted by preset (knowledge =
compact-early). Resolved per turn in `handle_sage_chat`; specialists carry it via
`SpecialistRuntimeContext.context_policy`. Both the proactive and background
compaction hooks honor the action.

### fresh_session mechanism proof (`_apply_fresh_session_context_policy`)
Ran against the real 102-turn `sage-main` thread:

```
summary_chars   = 947        (real summary generated by the agent's provider)
prior_messages  = 1          (carried into the current turn)
old session     = terminated
new session     = active, thread_id=sage-main,
                  source=context_policy_fresh_session, action=fresh_session,
                  carried_summary length = 947, parent = <old session id>
```

Action fires → session rotates → thread persists → summary carried. The
conversation survives coherently.

### Per-agent policy resolution proof
Set an install's `context_policy = {max_context_tokens: 500, on_context_full:
fresh_session}`; `resolve_specialist_runtime_context` surfaces it and the runtime
resolves `_ctx_policy_max=500`, `_ctx_policy_action='fresh_session'`.

Note on the `compact` action: it reuses the pre-existing, already-working
`conversation_compaction`; only the `fresh_session` action and the per-agent
policy plumbing are new, so `fresh_session` is what is proven end-to-end here.
The turn-triggered *background* firing is wired (both hooks sit on the per-turn
path and pass the turn's provider/model); its async flush is timing-dependent in
a short-lived script but reliable in the long-lived server, so it is proven at
the mechanism + resolution level rather than by a scripted background race.

## 5. Regression found and fixed mid-verification (named, not hidden)

Final verification surfaced a **broken `fleet/agents` endpoint** (deterministic
`duplicate key … agentdef_ws-1_sage`). Root cause was **my own Phase 1B tenant
resolver**, exposed by a concurrent test suite that polluted `ws-1` with 20
`tenant-1` agent installs (so ws-1 now spans two tenants: `default` = the 2 real
agents, `tenant-1` = 20 external-gateway test rows).

Three fixes, each with a clear root cause and proof:

1. **`control_plane_repository._tenant_id_from_installs`** — the installs
   fallback used `LIMIT 1` with **no `ORDER BY`**, so a multi-tenant workspace
   resolved to an arbitrary tenant. With `tenant-1` holding 20/22 rows it
   returned `tenant-1`, seeding the registry under the wrong tenant and colliding
   on the workspace-scoped master-definition id. Fixed: `ORDER BY created_at ASC`
   → the oldest install's tenant = the workspace's original owner (`default`).
   *This is what unbroke `fleet/agents`.*

2. **`sage_turn_adapter`** — tenant resolution used `get_workspace_by_id().tenant_id`,
   which returns `None` for legacy installs-only workspaces and, in mixed-store
   runtimes, can surface a polluting binding. That mis-attributed the **master**
   turn (usage recorded with a null agent). Fixed: route through the canonical,
   deterministic `resolve_tenant_id_for_workspace`. *This is what made the Sage
   usage row attribute to `ainstall_ws-1_sage`.*

3. **`sage_agent_runtime_service._apply_fresh_session_context_policy`** — the
   helper received `provider`/`model` but did not forward them to `compact_turns`,
   which then defaulted to deepseek and would produce an **empty summary**
   (continuity loss) on any non-deepseek agent. Fixed: forward provider/model.

### Pre-existing issues surfaced — flagged for a decision, deliberately NOT expanded into here

- **Non-idempotent registry seed.** `agent_registry_repository.ensure_workspace_agent_registry_seeded`
  uses **workspace-scoped ids** (`agentdef_{ws}_sage`, etc.) against
  **tenant-scoped** existence checks, across three inserts (definition, version,
  install). Any seed run under a non-owner tenant crashes on the duplicate id.
  Fix #1 removes the trigger for the real path; a durable fix (tenant-scoped ids
  **or** one-tenant-per-workspace enforcement **or** idempotent `ON CONFLICT`
  seeds) is a cross-tenant design decision, not a Phase 5 line-edit — left for
  the owner to direct.
- **`ws-1` tenant pollution.** 20 `extagent_*` installs under `tenant-1`
  (Hermes/OpenClaw/NemoClaw gateway test rows, all created today in one burst by
  a concurrent suite). Not mine; left in place because deleting another test's
  data blind is worse than the inert pollution (the resolver fix makes them
  invisible to ws-1's `default` fleet).
- **Ledger `install_id` not populated.** `hardware_grant_denied` events land in
  `activity_ledger_events` with the target id in the action metadata but the
  `install_id` column left empty — cosmetic; the event is unambiguous.
